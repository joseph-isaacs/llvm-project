# Re-run of 2026-09-05: correctness and performance status

Environment: `rustc 1.100.0-nightly (0ed41eb41 2026-09-04)` with LLVM 23.1.1 (the same commit as the
original report), `rustc 1.94.1` with LLVM 21.1.8, qemu-aarch64 8.2.2, x86-64 host (4 cores). The
reference `llvm-project` checkout used for source citations is upstream main at 833ee6a5c (2026-09-03).

## Correctness

No miscompile was found in nightly.

* `repro/qemu_test.rs` (the nine reproducers against reference implementations, exhaustive u8 and
  2M random u64 cases): passes on x86-64 natively for nightly and stable, and on aarch64 under qemu
  for nightly.
* `hunt2/diff_test.rs` + `hunt2/diff.sh` (new): drives all 138 hunt2 functions with seeded random
  inputs and prints one hash per function; the outputs from six builds are in `results/hashes-*.txt`.
  Nightly is identical across x86-64-v3, baseline x86-64 and aarch64, and identical to stable on both
  x86 targets, after canonicalising NaN and the sign of zero (both documented as unspecified for
  `f32::max`/`f32::min`).
* The only remaining difference is stable 1.94.1 on aarch64 for `max_f32` and `f_min_max_clamp`.
  `repro/snan.rs` isolates it: with a signalling NaN input, stable on aarch64 returns NaN from
  `f32::max(sNaN, 1.0)` while stable x86 and nightly on both targets return `1.0`, which is what the
  documentation promises. Nightly lowers `f32::max` to `llvm.maximumnum` (see
  `compiler/rustc_codegen_llvm/src/intrinsic.rs`, gated on LLVM >= 22); stable used `llvm.maxnum`,
  which AArch64 implements with a bare `fmaxnm` that propagates sNaN as NaN. This is the reason for
  the `fminnm x, x, x` instructions that appear on nightly, and is fixed, not a new bug.

## The nine findings

`repro/check.sh nightly` reproduces 1, 2, 3, 4, 5, 6, 8 and 9 exactly as described; 3, 4, 5, 6, 8, 9
and the `any_zero_byte` half of 2 reproduce on stable too, as the report says.

Finding 7 (`checked_abs` branch to fallthrough) reproduces with the default flags on nightly, in
isolation and in `repro.rs`, and not on stable. Two corrections to the hand-over:

* `repro/check.sh` reported it as "fine" because it counted jumps with `grep -cE '^\tj'`, and GNU
  grep does not read `\t` as a tab in that form. Fixed to `grep -c $'^\tj'`; the line now prints
  `2 REPRODUCES` on nightly and `0 fine` on stable.
* The pass is CodeGenPrepare's select-to-branch conversion, not SelectOptimize. SelectOptimize is
  behind `-disable-select-optimize` (default `true` in upstream `TargetPassConfig.cpp`; only AArch64
  and RISC-V add the pass themselves) and `-print-after-all` shows it never runs here.
  `-C llvm-args=-disable-cgp-select2branch` removes the branch; `-print-before/after=codegenprepare`
  shows the `br i1 %3, label %6, label %5, !prof` and the empty block `%5` being born in that pass.
  `isFormingBranchFromSelectProfitable` (`CodeGenPrepare.cpp`, ~line 7592) converts a select whose
  branch weights make it highly predictable when the target says predictable selects are expensive,
  which x86 does for out-of-order scheduling models.
* Why it is new in LLVM 23: stable's final IR has `select i1 %_3, i32 %_4, i32 undef` with no
  metadata, nightly's has the same select with `!prof !{"branch_weights", !"expected", i32 2000, i32 1}`,
  i.e. the `unlikely!` weights from `overflowing_neg` now survive SimplifyCFG's speculation onto the
  select. Forcing SelectOptimize on (`-disable-select-optimize=false`) gives the same asm, so both
  passes make the same decision on this input; the one that runs by default is CodeGenPrepare.

## 10. AArch64: `llvm.maximumnum`/`minimumnum` chains re-canonicalise values that are already quiet (new)

```rust
#[no_mangle] pub fn f_min_max_clamp(a: f32, lo: f32, hi: f32) -> f32 { a.max(lo).min(hi) }
```

IR: `%m = call nsz float @llvm.maximumnum.f32(%a, %lo); call nsz float @llvm.minimumnum.f32(%m, %hi)`.
Nightly aarch64 (MIR after `finalize-isel`, from `-C llvm-args=-print-after=finalize-isel`):

```
%3 = FMINNMSrr %1, %1          ; quiet lo
%4 = FMINNMSrr %0, %0          ; quiet a
%5 = FMAXNMSrr %4, %3
%6 = FMINNMSrr %5, %5          ; quiet the fmaxnm result: redundant, fmaxnm never returns an sNaN
%7 = FMINNMSrr %2, %2          ; quiet hi
%8 = FMINNMSrr %6, %7
```

Six instructions where five are needed. In `max_f32` (`fold(f32::MIN, f32::max)` over a slice) the
vector loop spends 8 of its 16 vector instructions on `fminnm v, v, v`, four of them on the four
accumulators, which are outputs of `fmaxnm` from the previous iteration and can never be signalling.
Stable emitted a bare `fmaxnm` per element (with the wrong sNaN semantics, see above), so the
2.3x growth in the loop body is the cost of the fix, and half of it is avoidable.

Where it comes from: `TargetLowering::expandFMINIMUMNUM_FMAXIMUMNUM`
(`llvm/lib/CodeGen/SelectionDAG/TargetLowering.cpp`, ~line 10331) lowers to `FMAXNUM_IEEE` and wraps
each operand in `FCANONICALIZE` unless `DAG.isKnownNeverSNaN(operand)`. `SelectionDAG::isKnownNeverNaN`
(`SelectionDAG.cpp`, ~line 6399) answers `true` for an `FMAXNUM_IEEE` result when asked about sNaN, but
for `FMINIMUMNUM`/`FMAXIMUMNUM` it only looks at the operands, so a chained `maximumnum` feeding
`minimumnum` gets a canonicalise on the intermediate value. The loop-carried case additionally needs
cross-block knowledge (the accumulator is a PHI), which a DAG-level check cannot have; that half would
need the IR-level `computeKnownFPClass` to drive the expansion, or a `fcanonicalize(fmaxnm(...))`
fold in the AArch64 DAG combiner. x86 is unaffected because it expands to compare-and-blend.
